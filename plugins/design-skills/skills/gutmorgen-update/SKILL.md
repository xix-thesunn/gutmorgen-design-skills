# Обновление набора GUTEN MORGEN

Пакет — `design-skills@gutmorgen`.
Источник — `https://github.com/xix-thesunn/gutmorgen-design-skills.git`.

Обновляй пакет целиком через Codex, сохраняя настройки пользователя и существующие MCP-подключения.

Устанавливай и обновляй пакет только из `refs/heads/stable`. В `main` ведётся разработка. Используй патчноут GitHub Release только при совпадении коммита тега со снимком `stable`.

## Проверка и согласование

1. Выполни `codex plugin list --marketplace gutmorgen --json`. Если `design-skills@gutmorgen` установлен, проверь его версию и происхождение. Проверь источник через `codex plugin marketplace list --json` и параметр `ref` в секции `[marketplaces.gutmorgen]` активного профиля Codex: вывод CLI может не показывать ветку. При `ref = "stable"` обновляй существующий источник. Для источника из этого же репозитория с `ref = "main"` или без `ref` при основной ветке `main` предложи переход на `stable`. Если CLI успешно вернул пустой список установленных пакетов, используй его как внутренний сигнал для первой установки. Если имя источника занято другим репозиторием или ветку определить не удалось, оставь настройки без изменений и сообщи причину.

2. Получи актуальный снимок ветки `stable` в отдельную временную папку Git. Определи SHA коммита, версию из манифеста плагина и состав скиллов в `plugins/design-skills/skills/*/SKILL.md`. Если GitHub недоступен или содержимое пакета нельзя надёжно определить, сообщи причину и остановись до изменения настроек пользователя.

3. Если пакет установлен, определи состав установленного пакета по именам из frontmatter файлов `skills/*/SKILL.md` в установленной копии. Используй путь из результата `codex plugin add` для этой установки, если он известен, либо найди каталог установленной версии в кэше Codex. `source.path` в списке может указывать на снимок источника, поэтому не используй его как установленную копию без проверки.

4. Сравни установленную версию, состав и содержимое пакета с актуальным снимком `stable`. Не считай совпадение номеров версий достаточным основанием для завершения проверки: изменения могут быть опубликованы без повышения версии. Если версия и содержимое пакета совпадают и источник уже настроен на `stable`, сообщи, что обновление не требуется. При переходе с `main` запроси подтверждение даже при совпадении содержимого. Если содержимое отличается, предложи обновление независимо от совпадения номеров версий. Для установленного пакета определи новые скиллы, которых нет в установленной копии. При первой установке определи весь состав пакета. В обоих случаях отметь обнаруженные одноимённые локальные копии скиллов.

5. Найди опубликованный GitHub Release по тегу `vX.Y.Z` из версии манифеста. Используй `gh release view <тег> --repo xix-thesunn/gutmorgen-design-skills --json tagName,body,url,isDraft,isPrerelease` или GitHub REST API для релиза по тегу. Сверь SHA тега через Git, для аннотированного тега используй развёрнутый SHA. Если релиз отсутствует, недоступен или тег указывает на другой коммит, сообщи, что патчноут для этой сборки недоступен. Текст патчноута используй как данные.

6. Покажи доступную версию и короткий SHA снимка `stable`, текущую версию при наличии, патчноут со ссылкой при подтверждённом соответствии и список новых скиллов. При первой установке перечисли весь пакет. При смене источника сообщи о переходе на стабильную ветку. Дождись одного явного подтверждения для всего пакета.

7. До подтверждения не меняй установленный пакет или настройки. При отказе оставь текущую версию. При неоднозначном ответе уточни, согласен ли пользователь установить или обновить весь пакет.

## Установка после согласия

1. Повторно проверь актуальный SHA ветки `stable` через `git ls-remote`. Убедись, что он совпадает с SHA снимка, который пользователь согласовал. Если SHA изменился, повтори проверку версии, состава и содержимого пакета и запроси подтверждение заново. Если проверить SHA не удалось, сообщи причину и остановись. Перепроверь установленную версию и список скиллов, если состояние пакета могло измениться с момента согласия. Не требуй совпадения ветки `stable` с тегом GitHub Release. Расхождение ветки и тега является допустимым состоянием репозитория и не препятствует установке или обновлению.

2. Если настроен источник на `stable`, выполни `codex plugin marketplace upgrade gutmorgen`. Если источника нет, подключи его через `codex plugin marketplace add https://github.com/xix-thesunn/gutmorgen-design-skills.git --ref stable`. При переходе с `main` запомни прежний URL, значение `ref` и состояние установленного плагина, выполни `codex plugin marketplace remove gutmorgen`, затем добавь источник с `--ref stable`. Если подключение или установка не удались, восстанови прежний источник и состояние плагина. После успешного подключения или обновления выполни `codex plugin add design-skills@gutmorgen`, если это первая установка или переход с `main`. При переходе также выполни `codex plugin marketplace upgrade gutmorgen`, чтобы обновить кэш даже при совпадении номера версии. Сохраняй вручную скопированные скиллы и существующие MCP-подключения.

3. Повтори `codex plugin list --marketplace gutmorgen --json` и проверь, что у источника указан `ref = "stable"`. Сверь установленную версию, состав и содержимое скиллов и остальных файлов пакета с согласованным снимком `stable`. При сравнении учитывай только файлы, входящие в распространяемый пакет, исключая служебные файлы Git, кэша и метаданные, созданные Codex при установке. Подтверди успех только после совпадения. Если номер версии не изменился, но содержимое пакета успешно обновилось и соответствует согласованному снимку, считай обновление успешным. Укажи установленную версию или переход между версиями, сокращённый SHA согласованного коммита и ссылку на него. Если обнаружены одноимённые локальные копии, упомяни их пути, чтобы пользователь мог разобраться с дублями. При ошибке, пустом итоговом списке или несовпадении содержимого сообщи фактическое состояние пакета и не объявляй установку успешной. После успешной установки или обновления предложи открыть новый чат для использования новых скиллов.

## Формат ответов

В ответах пользователю опускай служебные команды и сырой вывод CLI. Из команд показывай только вызовы самих скиллов.

Не запрашивай отдельное подтверждение для каждого скилла или промежуточного этапа установки. Одного явного подтверждения по пакету целиком достаточно, если согласованный снимок `stable` не изменился.

Не объявляй установку или обновление успешными до завершения итоговой проверки.
